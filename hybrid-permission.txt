Yes. **The plan is structurally good, but I would not execute it exactly as written.** There are several important issues to fix first—especially around permissions, `SUPER_ADMIN`, `roleId`, and the route mappings.

I’d rate it **8/10 as an implementation plan**. With the changes below, it becomes a solid production-style hybrid RBAC implementation.

## 1. The architecture is correct

The overall direction is right:

```text
Permission Catalog
       ↓
Role Collection
       ↓
User → roleId
       ↓
Role.permissions[]
       ↓
hasPermission()
       ↓
Scope / Business Rules
       ↓
ALLOW / DENY
```

And keeping the existing:

```js
authorize(...)
```

temporarily while introducing:

```js
hasPermission(...)
```

is a good migration strategy.

The biggest advantage is that you can migrate route-by-route instead of rewriting the whole backend at once.

The idea of:

```text

PERMISSION_MODULE_MAP
```

is good.

But don't decide **"60 permissions"** first and then force the application into 60.

Instead:

> Generate the permission catalog from the actual resources/actions your backend currently has.

Your existing detailed RBAC design already has granular actions such as:

```text
products.read

products.update
products.delete
products.publish

orders.read
orders.confirm
orders.process
orders.ship
orders.deliver
orders.cancel
orders.return
orders.refund

reviews.approve
reviews.reject
```

That's better than arbitrary broad permissions like:

```text

orders.manage
reviews.moderate
```

### Keep

```js
PERMISSIONS = Object.freeze({...})
PROTECTED_PERMISSIONS = [...]
PERMISSION_MODULE_MAP = {...}
```

But make the catalog **the result of your actual authorization requirements**, not a target number.

# 3. Phase 2 — `roleId` + `role` needs caution

The plan says:

```text
user.roleId
+
existing user.role
```

and a pre-save hook keeps both synchronized.

This is useful during migration, but **I would not use a pre-save hook as the main synchronization mechanism.**

Why?

You can have:

```js
User.findByIdAndUpdate(...)
```

which doesn't necessarily behave like a normal `save()` lifecycle.

You could end up with:

```text
role = ADMIN
roleId = PRODUCT_MANAGER
```

That's exactly the inconsistency you're trying to prevent.

### Better migration

During migration:

```text
role       → legacy compatibility
roleId     → new source of truth
```

Then explicitly synchronize them in your user/role service.

Even better:

```text
roleId → authoritative
role    → temporary legacy field
```

After all old code has migrated:

```text
REMOVE role
```

Don't keep dual fields permanently.

# 6. Protected permissions need a stronger design

This is the biggest issue in the proposed plan.

It says:

> `updateRolePermissions()` rejects any payload containing `PROTECTED_PERMISSIONS`.

But Phase 6 says:

```text
SUPER_ADMIN → All permissions (including protected)
```

Those two ideas conflict.

If the API rejects protected permissions for everyone, how does the Super Admin role get them?

You need:

```text
Protected permission
        ↓
Can only exist on SUPER_ADMIN
        ↓
Cannot be assigned to custom roles
        ↓
Cannot be removed from SUPER_ADMIN
```

For example:

```text
roles.manage
permissions.manage
staff.manage
settings.update
audit.read
super_admin.manage
```

The exact list depends on your application.

### Important

Don't rely on:

```js
if (user.role === "SUPER_ADMIN")
```

everywhere.

Instead, mark the system role:

```js
isProtected: true
```

and enforce the invariant centrally.

# 7. SUPER_ADMIN bypass is acceptable, but I'd modify it

The plan says:

```text
SUPER_ADMIN bypass
```

This is common and practical.

But don't make it a blanket bypass for absolutely everything without thought.

For normal business permissions:

```text
SUPER_ADMIN → ALLOW
```

Fine.

For protected system operations:

```text
SUPER_ADMIN → ALLOW
```

Fine.

But **business policies still apply**.

For example:

```text
SUPER_ADMIN
    orders.refund
        ↓
Order refundable?
        ↓
Payment captured?
        ↓
Refund amount valid?
```

RBAC shouldn't bypass your business rules.

# 8. Phase 5 has an important security problem

The plan says:

```text

GET/POST/PUT/DELETE /api/admin/roles
```

and:

```text

```

for all routes.

That's mostly okay.

But don't give every operation the same permission.

Use:

```text

```

Then:

```text

DELETE roles    → roles.delete
GET catalog     → permissions.read
```

And still enforce:

```text

```

for protected RBAC management.

This gives you much better auditability.

# 10. `ADMIN = all business permissions except protected` is risky

This:

```text
ADMIN → All business permissions except protected
```

is convenient, but I'd avoid defining your production policy this way.

Explicitly define Admin's permissions.

Why?

Tomorrow you add:

```text
system.backup
developer.tools
database.export
payment.keys.read
```

If you automatically give Admin "all non-protected permissions", you've accidentally expanded Admin's access.

Instead:

```text
ADMIN
    explicitly assigned business permissions
```

Then when you add a new permission:

```text
new permission → DENY by default
```

This is **least privilege**.

# 21. Add role protection rules

You should define:

```text

    isSystemRole = true
    isProtected = true
```

and:

```text

    isSystemRole = true
```

etc.

Then decide which roles can be deleted.

I recommend:

```text
SUPER_ADMIN         → cannot delete
ADMIN               → system role, cannot delete
PRODUCT_MANAGER     → system role, cannot delete
ORDER_MANAGER       → system role, cannot delete
SUPPORT_EXECUTIVE   → system role, cannot delete
CUSTOMER            → system role, cannot delete
Custom roles        → can delete
```

Why?

Your six default roles should be **protected system roles**.

Super Admin can modify their permissions where appropriate, but shouldn't accidentally delete the application's fundamental roles.

## Final answer

**Yes, this is a good plan to start from. But don't give it to VS Code AI and say "execute exactly this."**

I'd first correct these **8 things**:

1. ❗ Don't use `*` permissions such as `orders.*`; use explicit permissions.
2. ❗ Don't give Admin "all business permissions" automatically; explicitly define them.
3. ❗ Make `roleId` the eventual source of truth; `role` is temporary.
4. ❗ Protected permissions need special handling for `SUPER_ADMIN`.
5. ❗ Add protected system roles and **last Super Admin protection**.
6. ❗ Add dedicated RBAC/permission API integration tests.
7. ❗ Keep scope/business rules separate from permission checks.
8. ❗ Skip Redis for MVP.

With those changes, **the hybrid RBAC architecture is the right approach for RigCraft**. It gives your Super Admin dynamic control over role permissions while keeping the permission catalog, security boundaries, scopes, and business rules controlled by the backend.
